# PF12.1 follow-up: visible matrix illumination before launch

2026-10-02. This correction supersedes the presentation acceptance claims in
`pf12.1-matrix-handoff.md`. The PF12.2 report remains an audit of its pinned
candidate, not a claim that the subsequent user-observed bug was absent.

## Root cause

The first fix populated `Display.Dots` but deliberately preserved `Display.On`
and outgoing flash state. The ball-loss program executes `_MATRIXLGT,0`.
Consequently the next player's logical score/player/ball glyphs existed while
their palette remained off. The previous test inspected only logical dots,
so it incorrectly accepted the user's visibly blank screen. This also affects
single-player new balls and is shared by the other tables' normal handoffs.

## Lifecycle correction

`Display.ShowPlayerBall` now commits both the existing source idle glyphs and
their steady illumination: `On=true`, `flashSpeed=0`. Its existing callers are
the completed `Session.Advance`/incoming player-state load boundary and new-ball
initialization before SETBALL. Nothing is forced per render tick. The display's
command, elapsed, animation, scrolling and other state remains intact.

Source evidence: historical `FANTASIE.ASM`'s `DO_THE_ANIMATIONS`, `ts_slut` calls
`KILL_FLASHOR`; that routine stops MATRIX_IS_FLASHING and restores MATRIXON.
This is lifecycle evidence, not a license assertion. Gameshow/Stones PARTYFLASH
shoot-again messages bypass the idle-panel replacement and retain source flashing.
There are no production physics/audio/session/score-formatting changes.
