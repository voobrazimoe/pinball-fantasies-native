# PF12.1 matrix presentation at player/new-ball handoff

**Follow-up correction:** this first fix missed the display illumination gate.
Its logical-only presentation acceptance was insufficient. See
[matrix-illumination follow-up](pf12.1-matrix-illumination.md) for the corrected
visible-frame tests, source illumination restoration and owner-approved image
oracle update. The results below describe the earlier pinned fix.

The containing private-main commit delivers this focused fix. PF12.2 is paused;
its uncommitted audit drafts and pre-existing stash are excluded from this commit.

## Root cause and source boundary

`advancePlayer` saved the outgoing slot, advanced the session, loaded the incoming
slot and updated source text buffers, but never committed the logical dots. The
later multiplayer `newBall` started `SHOWPLAYERSTS` at its transition clear and
left score display to `Frame`'s idle fallback. Single-player new balls did not
start that program at all. This separated identity/state selection from logical
matrix presentation. A headless probe reproduced zero logical dots at Party's
handoff and delayed player/ball prints; a render fallback could conceal the gap.
No claim is made that every host reproduces an indefinite blank identically.

Stones additionally kept the old `_CHANGE_PLAYER` program active: its following
clear could erase the incoming presentation during the new-ball delay. The other
three tables already retired that outgoing program.

The historical shared `WHEN_NEW_BALL_RESET` routine in FANTASIE.ASM updates score
and selects `SHOWPLAYERSTS` before launch, except when PARTYFLASH deliberately
retains the table's shoot-again/party presentation. Table `_CHANGE_PLAYER` routines
save the outgoing state and select/load the incoming state before NEW_BALL_TASK.
These source references are lifecycle evidence, not an upstream license claim.

## Fix

After successful `Session.Advance`, incoming `LoadPlayerState` (multiplayer) and
`playerText`, each table's `advancePlayer` now commits the logical idle panel.
After transient new-ball initialization, `newBall` re-establishes that panel
before its scheduled SETBALL/launch readiness. This covers single-player too.

`presentation.Display.ShowPlayerBall` draws that table's existing static
SHOWPLAYERSTS print commands with extracted text and resolved positions. It uses
the existing CODE2 `Score` renderer without changing zero/BCD formatting. It
commits dots once per lifecycle boundary, without running the delayed transition
clear. A copy preserves the live display's command, elapsed, animation, scrolling
and flashing state; it neither resets the engine nor paints every render tick.

Gameshow/Stones retain their legitimate PARTYFLASH shoot-again messages through
new-ball initialization. Party/Speed's existing transient reset finishes those
messages and restores the source player/ball panel. Stones retires its obsolete
outgoing loss program at `_CHANGE_PLAYER`, matching the other tables. No frontend
production rendering logic, physics, audio, player rotation or scoring changes.

## Focused regression

`internal/frontend/handoff_presentation_test.go` checks the logical Display.Dots,
never Frame's synthetic idle fallback. It starts through the frontend, uses real
plunger input for each outgoing ball, places only that ball below the drain as an
explicit test fixture, and runs actual loss/bonus/task scheduling. It does not call
changeBall/newBall directly or launch the incoming ball to obtain its first panel.

On the exact sync changing active player/round it checks source player/ball text
and correct current score, then checks every sync for 710 idle ticks (ten source
seconds). Normal SETBALL positioning/hold release may complete; no plunger charge,
launch or gameplay progression is allowed. Zero scores use the existing renderer.
