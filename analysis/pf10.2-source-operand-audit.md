## 0. Scope and result

A live Stones crash was observed:

```text

  internal/stones.(*Game).numeric      internal/stones/matrix.go:54
```

## 1. Opcode schema

Authority: the original DOS retail assembler. Arity and operand roles are read
from the handlers themselves, not from the Go port:

* `FANTASIE.ASM` — the shared interpreter (`DO_SPEC_MATRIX`, `_ANIMATION`,
  `_SCROLL`, `_NUMBER`, `_FLASHON`, `_FLASHOFF`, `_MATRIXLGT`, `_SETDECCOR`,
  `_WAIT`, `_WAITifmulti`, `_JINGLE`, `_SOUND_EFFECT`, `_lastjingle`,
  `_countdown`, `_COUNTDOWNCONTINUE`, `print_end`, `three_end`, `NORMAL_END`).
* `PLAND.ASM` / `SDEV.ASM` / `SHOW.ASM` / `STONES.ASM` — table-local handlers
  (`_JMP`, `_JBCDZ`, `_JBONUSX1`, `_SHOW_SCORE`, `_LOOP_`, `_SETLOOP`,
  `_tower`, `_PARTYON`, `_KNACKET`, effect-mode switches, …).

The operand count is derivable from the handler's own `BX` advance:
`NORMAL_END` → `ADD BX,4` (1 operand word), `print_end` → `ADD BX,6` (2),
`three_end` → `ADD BX,8` (3), and the branch handlers read `[BX+2]`/`[BX+4]`
directly. The schema is machine-readable in
`tools/matrix_operand_schema.py` (`OPCODES`), with a source citation per opcode.

Operand kinds:

| kind | meaning | example |
|---|---|---|
| `NUM` | integer copied into a counter, position or row | `_WAIT,2*60`, `_TOWER,36-16`, `_PRINT13,_,SW*4/4+TOTCENT+4` |
| `LBL` | matrix program destination | `_JMP,NO_BONUS2TS`, `_JBCDZ,OR_TOTAL,NO_ORTS` |
| `TXT` | text/scroller DATA identity (or `_CLEAR`) | `_SCROLL,BEATENSCROLL` |
| `ANIM` | animation identity | `_ANIMATION,_EXTRABALL` |
| `VAL` | runtime value/BCD row identity | `_PRINT13_NUMBER,BONUSSIFFRORNA,_` |
| `JIN` | jingle identity | `_JINGLE,S_BEATEN` |
| `SND` | sound-effect identity | `_SOUND_EFFECT,S_MULTILJUD,0` |
| `FLG` | numeric operand consumed as a boolean | `_MATRIXLGT,1` |
| `IGN` | word the original handler never reads (`?` placeholder or filler) | `_FLASHOFF,?`, `_PARTYON,1` |

61 distinct opcodes are used across the four retail tables (53 F1, 56 F2,
54 F3, 61 F4). Every one is in the schema; the checker fails on an unknown
opcode or an operand-count mismatch.

## 3. Arithmetic-expression audit

211 reachable operands are arithmetic expressions. The grammar actually present
in retail source is exactly: integer literals (decimal and `NNh` hex),
parenthesised sub-expressions, `+ - * /`, unary signs, and table equates. There
are no shifts in matrix operands. `tools/matrix_operand_schema.py:resolve_expression`
implements that closed grammar and raises `OperandError` on anything else —
it is not a general evaluator and it never runs at gameplay time. It resolves
during extraction only.

## 4. Symbol resolution

Equates are recovered from each table's own ASM over the whole file, including
the in-stream assignments that appear between matrix commands
(`SHOWTIME=80`, `DRSPEED=13`, `LMSPEED=7`, `PARTY_ON_SPEED=3`,
`SHOOT_AGAIN_SPEED=3`, `MILESWAIT`, `JMP_T`, `TOTCENT=16`, `SW=336`).

Two symbol problems were found and fixed:

1. **`EMPTYJINGLE` did not exist in any surviving source.** It is referenced by
   the matrix streams (`DW _LASTJINGLE,EMPTYJINGLE`) but declared in a lost
   include. Every table declares `S_Empty DB <position>,<repeat>,<priority>`,
   and `EMPTYJINGLE` is that empty-jingle music position: 62 / 55 / 55 / 52 for
   F1/F2/F3/F4 — exactly the values the native port had hardcoded in four
   separate runtime helpers. It is now recovered from source
   (`schema.empty_jingle_position`) instead of hardcoded per table.
2. **`SW` meant two different things in the extractors.** `reference_pf45.py`
   and `reference_pf7.py` seeded `SW=320`; `reference_pf8.py` used the
   documented memory stride `SW=336`. Nothing noticed while only `_WAIT`/timing
   values were resolved, because `SW` appears only in matrix position
   expressions. As soon as positions became typed operands, F1/F2 resolved
   `SW*4/4+TOTCENT+4` to 340 instead of the source 356. Both extractors now use
   the source-proven 336, and the audit cross-checks the typed value against the
   generated provenance map.

`tools/matrix_operand_audit.py` fails if any symbolic numeric operand cannot be
resolved.

## 9. Exact `2*60` root cause

```asm
; STONES.ASM:1470
SKILLSHOTTS:
        DW _RULLGARDIN_UPP,SKILLTEXT,1
        ...
        DW _WAIT,2*60              ; STONES.ASM:1475
```

* Opcode: `_WAIT`, operand index 0 (`FANTASIE.ASM:_WAIT` → `MOVE SISA,[BX+2]`).
* Source meaning: 120 native syncs of matrix hold — `2 * 60`.
* Correct integer: **120**.
* Extractor before: `reference_pf8.py` split the `DW` line and kept the raw
  token `"2*60"` in `args`. Only `_PRINT*`/`_RULLGARDIN*` second operands and
  `_TOWER` were evaluated into the `positions` map; `_WAIT` was not.
* Why `numeric()` saw it: `STONES.ASM:1598` is the second instance in
  `MILLIONPLUSTS`. `matrixDispatch` case `_WAIT` ran
  `m.left = num(0)` → `g.numeric("2*60")` → `strconv.Atoi` failed →
  `panic("STONES integer " + s)`.
* Route: `SKILLSHOT`/`MILLIONPLUS` effect record → `EFFECT` handler →
  `beginMatrix("SKILLSHOTTS"/"MILLIONPLUSTS")` → `matrixDispatch()` → first
  `_WAIT` dispatch panics.

Reproduction is now deterministic:
`internal/stones/matrix_operand_test.go:TestStonesWaitExpressionOperandsResolved`
drives both programs through the real dispatcher, asserts `Num(0)==120` while
`Args[0]=="2*60"` is retained for provenance, then ticks the real scheduler
through the wait. Deleting the `nums` entry from the generated command makes the
real VM panic with `unresolved source operand _WAIT[0]="2*60"`, and
`TestStonesReachableProgramsOperandSmoke` fails — verified while developing this
audit.

## 11. Recommended extraction/runtime architecture

Implemented in the isolated copy:

```text
ASM expression
  -> extractor resolves the exact integer (closed assembler grammar, source equates)
  -> generated command keeps raw source text in Args (diagnostics + identity keys)
     and carries the typed integer in Nums[operand index]
  -> runtime consumes Nums; a missing entry panics
```

* `tools/matrix_operand_schema.py` — the single schema + resolver used by all
  three extractors and by the checker. No expression interpreter was added to
  gameplay.
* `Command.Nums map[int]int` (presentation), `matrixCommand.Nums`
  (partyland), `command.Nums` (speeddevils).
* `presentation.Display.BeginCommand` / `BeginResolved` feed the resolved
  values to the renderer; `Display.Num(i)` panics instead of defaulting.
* `Display.PositionValue(int)` is the runtime geometry path; the
  `Content.Positions` string map is retained as provenance and for the two
  synthetic frontend replay programs (`GameOver`) and unit tests.
* `Display.Num`'s literal fallback exists only for those synthetic programs and
  rejects anything that is not a plain decimal.

No default-zero, no silent parse failure, no fallback row, no ignored command
and no numeric substitution was added. Missing operands remain invariant
violations.

## 17. Extension — DATA text bytes and runtime text write-back

A live Speed Devils report ("the left ramp shows `XXX MILES` and `0 0 … lites
off road`") exposed two further defects in the same source-authority theme but
in the *text data* layer rather than the operand layer. Both are now covered by
the checker.

### 17.1 `DB` byte expressions were split into two bytes (same class as PF10.2)

Retail text DATA mixes character literals with arithmetic. Each comma-separated
element is one byte; the extractor's quote-first tokenizer turned them into two:

| table | source | old generated | rendered | correct |
|---|---|---|---|---|
| F2 | `SDEV.ASM:1819 DB '7'+2,'7 LITES EXTRA BALL'` | `0x37,0x02` | `0 0 LITES EXTRA BALL` | `20 LITES EXTRA BALL` |
| F2 | `SDEV.ASM:1820 DB ' ','7'+1,'7 LITES OFF ROAD'` | `0x20,0x37,0x01` | `0 0 LITES OFF ROAD` | ` 10 LITES OFF ROAD` |
| F3 | `SHOW.ASM:1299 DB '  MONEY MANIA AT ',6+'7',' '` | `0x06,0x37` | `MONEY MANIA AT 0` | `MONEY MANIA AT 6` |
| F4 | `STONES.ASM:1873 DB 'XXX LITES ','7'+5,' MILLIONS'` | `0x37,0x05` | `XXX LITES 0 MILLIONS` | `XXX LITES 5 MILLIONS` |
| F1-F4 | `ZEROQ DB '0'+7,0` | `0x30,0x07` | `0` + stray cell | `0` |
| F3 | `SHOW.ASM:108 SPINscores DB 0,0,0,'*'-'A'+10,…` | truncated to 4 bytes | — | full 12-byte row |

The reported `0 0 … lites off road` is exactly row 2: the encoded `1` became a
control byte plus a literal `0`.

Fix: `tools/matrix_operand_schema.py` gained a top-level comma splitter plus
`db_element_bytes`/`db_bytes`, which evaluate a whole element with the
assembler's byte semantics (character literal = code point, result truncated to
a byte). `reference_pf8.py` uses it for the text tables. `DUP` repeat counts are
themselves expressions (`16*16 DUP (0)`, `576*2 DUP(0)`), so `_dup_count`
evaluates them; a naive `int()` had made `UNDANSPR` 17 instead of 256 and
`HIDDA` 3 instead of 1152. `reference_pf7.py`/`reference_pf45.py` use the
lenient `db_byte_count` for their length-only tables so no entry is ever lost to
an uninitialised `?` row or a lost-include symbol (all `_SCROLL` argument counts
are unchanged).

Checker coverage: `text_data` in `tools/matrix_operand_audit.py` re-derives
every source `DB` element and compares it with the generated buffer — currently
1106 source texts, **0 byte mismatches** — and the Go test
`TestSourceTextBytesMatchAssemblerExpressions` pins the corrected renderings.

### 17.2 The original writes live counters into text buffers (different class)

`MILES_TEXT` is declared `DB '     XXX MILES      '`; the `XXX` is a
placeholder the original overwrites at runtime:

```asm
; SDEV.ASM:4773-4774  NotStandardSeries -> Put_In_Text (SDEV.ASM:4795)
mov  bx,5+offset miles_text
mov  ax,cyclonecounter
call put_in_text          ; three encoded digits at miles_text[5..7]
```

The same pattern writes `JUMP_AT_TEXT[0..2]` and `OFFROAD_AT_TEXT[0..2]` from
`NextJump`/`NextOffRoad` (SDEV.ASM:4721-4763). The port rendered the raw
template, so the ramp showed `XXX MILES` and `XXX LITES …`.

This is *not* the operand-resolution class — the operand (`MILES_TEXT`) is a
correct text identity; what was missing is the runtime write-back into the
source DATA buffer. PF10.2's operand layer cannot see it, because it classifies
text operands as identity-only.

Fix (Speed Devils): `internal/speeddevils/presentation.go` gained
`putInText`/`putInTextTopZero` (exact `Put_In_Text` and jump/off-road loop
semantics, including the `'*'` blank for a leading zero) and
`writeMilesText`/`writeJumpText`/`writeOffRoadText`, called from the real
`loop()` award path. `sourceTextBuf` copies before writing, because the
extracted byte slices are shared between displays; a second game still sees the
untouched template.

Tests: `internal/speeddevils/source_text_test.go` covers the extracted bytes,
all four counter encodings (`0`, `7`, `20`, `123`), the real award path, and
buffer isolation between games.

### 17.3 Remaining text write-back gaps (inventoried, not fixed)

The checker now lists every text buffer that a matrix program prints *and* the
original writes at runtime but the port does not:

```text
runtime-mutated text buffers without a native writer 3
   -- Gameshow:BONUS_X_TEXT     (SHOW.ASM:3978  MOV BONUS_X_TEXT[8],AL)
   -- Gameshow:SKILLTEXT        (SHOW.ASM:3699  Put_In_Text into SKILLTEXT+16/17)
   -- Stones ’N Bones:BONUS_X_TEXT (STONES.ASM:5726)
```

Party Land and Speed Devils report none. These three are the same class as
17.2 and are listed as informational output rather than a hard failure, because
each needs a rule-layer hook (bonus multiplier / skill multiplier) rather than
an extraction fix.

## 18. Limits

* This is static source/data analysis. It proves operand *resolution*, not that
  every presentation behaviour is pixel-exact.
* Reachability is the PF10.1 source graph; runtime state selectors (effects,
  lamps, counters) are covered by the existing PF10.1 families and by the
  bounded per-program Stones smoke.
* `tools/matrix_operand_audit.py` treats a bare `CLEARIT` macro as the table's
  real clear opcode; that mapping is declared in `CLEAR_OP` and cross-checked
  against the extractors.
* The audit does not touch `.HI` score files, the Amiga/CD32 trees, or any
  artwork/audio fixture.
